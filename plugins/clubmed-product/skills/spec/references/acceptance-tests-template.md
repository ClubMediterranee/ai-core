# §9 Acceptance Tests — template

Canonical structure for the **§9 Acceptance Tests** section of a spec generated by the `spec`
skill. The scenarios are **standard Gherkin** (parseable by Cucumber and consumable by the
`e2e-test-generator` skill) — not a markdown look-alike. §9 derives entirely from §5 Business
Rules and the PRD's `FUNC`/`BR`/`ERR` ids. It is **drafted in Step 5** (from the PRD alone) and
**finalized in Step 6.7**, where the error cases discovered against the real API (expiry, conflict,
availability) become non-passing scenarios — then written with the rest of the file in Step 6.8.

---

## Machine anchor (required — do not translate, do not drop)

The section heading carries a stable anchor `<!-- at:tests -->`. The validator detects §9 by this
anchor, so it survives a localized heading.

## How the global language rule applies to Gherkin

The spec's language is set globally (`SKILL.md` § Language). Gherkin carries it through its **own
localization**, so the keywords are translated too:

- **French** → first line `# language: fr`, then `Fonctionnalité`, `Scénario`, `Étant donné`,
  `Quand`, `Alors`, `Et`.
- **English** → no `# language` line (the default), `Feature`, `Scenario`, `Given`, `When`, `Then`, `And`.

**One language per block**: never mix a French keyword with English steps, and never use French
keywords without the `# language: fr` header — both are invalid for a real Gherkin parser and for
`e2e-test-generator`. **Tags stay canonical English** in every language (machine tokens).

---

## Scenario types — a completeness checklist, not a quota

Cover **every observable behaviour and every in-scope ERR** of the spec. The five types below are the checklist that keeps you honest about what might be missing — never fabricate a scenario just to tick a box:

1. **Nominal passing** — the happy path of the spec's main FUNC.
2. **Nominal non-passing** — the main path fails / a guard rule (BR) is violated.
3. **Alternative passing** — a secondary valid path (another FUNC/BR the spec covers).
4. **Alternative non-passing** — the secondary path fails.
5. **Edge case** — a boundary or rare condition (empty state, missing data, limit value).

If a type genuinely does not apply (e.g. the spec has a single path and no alternative), **skip it
and say why** in one line above the block. **Skip a scenario entirely** when it would only document
an implementation detail — that belongs in unit tests, not in an acceptance spec.

## Tags — one category tag + at least one trace tag per scenario

Every `Scenario:` is preceded by Gherkin tags:

- **Exactly one category tag:** `@nominal-passing` · `@nominal-non-passing` · `@alternative-passing` · `@alternative-non-passing` · `@edge`.
- **At least one trace tag** to the PRD ids the scenario exercises: `@FUNC-001`, `@BR-001`, `@ERR-002` (also `@ACC-xxx`, `@PERM-xxx`, `@ST-xxx` when relevant). Every id used must be defined in **this** spec's §5.

**Coverage rule (enforced by the validator):**
- at least one passing scenario (`@nominal-passing` or `@alternative-passing`);
- **every `ERR-xxx` referenced in §5 has at least one non-passing scenario** tagged with that ERR id;
- every scenario carries at least one trace tag.

## Structure — paste as section 9 of the spec (everything localized; only tags and the anchor stay canonical)

Example shown for a **French** spec. For an English spec, drop the `# language: fr` line and use
`Feature` / `Scenario` / `Given` / `When` / `Then` / `And`; the tags are identical in both.

````markdown
#### 9. Tests d'acceptance   <!-- at:tests -->

> Gherkin standard, traçable au §5. Tags : une catégorie + les ids `FUNC/BR/ERR` exercés.
> Consommable par le skill `e2e-test-generator`.

```gherkin
# language: fr
Fonctionnalité: <titre du spec>

  @nominal-passing @FUNC-001 @BR-001
  Scénario: <label — chemin nominal>
    Étant donné <contexte / précondition>
    Et <précondition supplémentaire>
    Quand <événement déclencheur>
    Alors <résultat observable>

  @nominal-non-passing @BR-001 @ERR-002
  Scénario: <label — échec du chemin nominal>
    Étant donné <contexte>
    Quand <événement qui viole BR-001 / déclenche ERR-002>
    Alors <comportement d'erreur attendu>

  @alternative-passing @FUNC-002 @BR-003
  Scénario: <label — chemin alternatif valide>
    Étant donné <contexte>
    Quand <événement>
    Alors <résultat observable>

  @alternative-non-passing @ERR-004
  Scénario: <label — échec du chemin alternatif>
    Étant donné <contexte>
    Quand <événement>
    Alors <comportement d'erreur attendu>

  @edge @BR-017
  Scénario: <label — cas limite>
    Étant donné <condition limite : donnée absente, valeur extrême, état vide>
    Quand <événement>
    Alors <résultat observable>
```
````

## Notes for the author

- **Standard Gherkin, not markdown.** No bold `**Étant donné:**` / `**Given:**`; use the bare
  keywords so a real Gherkin parser and the `e2e-test-generator` can consume the block.
- **One language per block.** French keywords require the `# language: fr` first line; English
  keywords require no header. Mixing the two is invalid — see the Language section above.
- **One observable outcome per scenario.** Multiple `Given` (stacked preconditions) is fine; multiple
  independent `When`/`Then` is a smell — split the scenario (and probably the spec).
- **Trace, don't restate.** A scenario proves a rule; it references the rule's id via a tag rather
  than paraphrasing the whole BR.
- **ERR coverage is mandatory.** Each `ERR-xxx` the spec's §5 lists must have a non-passing scenario —
  the error path is a first-class outcome, not an afterthought.
