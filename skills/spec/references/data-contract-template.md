# §8 Data Contract — template

Canonical structure for the **§8 Data Contract** section of a spec generated by the `spec`
skill. This content lives **inside** the spec file (`{DOCS_ROOT}/specs/<prd-slug>/<spec-basename>.md`) as its
section 8 — there is no separate artifact and no separate frontmatter. The resolution metadata is
surfaced in the spec's own frontmatter (`data_contract_confidence`, `data_contract_sources`) and in
the §8 intro note. The rules that govern this section are in **Notes for the author** at the end.

---

## Language

The labels below are the **canonical English reference**. Render §8 in the user's language per
`SKILL.md` § Language — translate every label naturally (there is no fixed dictionary), and leave
the machine tokens (anchors, identifiers, code) untouched.

---

## Confidence tier (house style)

```
**Confidence:** 🟢 high · <evidence>
```

- Tiers: `🟢 high` · `🟡 medium` · `🔴 low`, mapped from `references/confidence-rubric.md`.
- **No numeric percentage and no progress bar.** The bucket *is* the granularity — attaching
  a `90%` or a `■■■■■□` bar would be fabricated precision the sources do not support.
- `<evidence>` is **mandatory** for `🟢 high`: `validate_route → is_valid: true`, or
  `API op <operationId>`, or `DRD <Component> Content Contract`. No evidence → not `🟢`.
  **An API scenario is never evidence** — scenarios are the API team's documentation used to
  *find* routes (see below); they prove nothing about a field path or a CMS key.

## API scenarios are a discovery aid — never spec content

The `clubmed_api` MCP also serves **scenarios written by the Club Med API team to document the
API** (they are what makes the MCP searchable). Use them in Step 6 to **find the right routes and
the order to call them** — that knowledge shapes the endpoint index and the call order shown in
the TypeScript. **Nothing about the scenario itself is written into the spec**: no scenario id,
no "business journey" sub-section, no channel gating. A spec documents the *contract* the
developer must implement, not the internal API documentation used to discover it.

## Severity (Points to clarify) — text labels, not traffic lights

Severity is **Blocking / Medium / Minor**, written as text. The traffic-light emojis
`🟢🟡🔴` are **reserved for confidence** — never reuse them for severity, or the reader cannot
tell an axis from the other.

- **Blocking** — blocks implementation or forces a design decision (which endpoints to build).
- **Medium** — a field / enum / body is unconfirmed but has a reasonable default.
- **Minor** — cosmetic or already worked around.

---

## Base URL

The API base URL comes from the OpenAPI `servers` block — **confirm it via the MCP**. If the
MCP does not expose a `servers` entry, look for a host hint in the operation examples'
`_links[].href` values and offer it **as a hypothesis** in Points to clarify (not as fact),
keeping the `<API_BASE_URL>` placeholder in the curl/TypeScript. **Never hardcode a host you
have not verified** (a wrong host ships a non-executable curl as if it were proven).

## Machine anchors (required — do not translate, do not drop)

The three mandatory §8 sub-sections each carry a **stable HTML-comment anchor** on their heading:
`<!-- dc:clarify -->`, `<!-- dc:index -->`, `<!-- dc:handoff -->`. They are invisible in the
rendered markdown and **language-independent** — the human label beside them is translated freely,
but the anchor never changes. `scripts/validate_specs.py` detects the sub-sections by these anchors,
so an anchor that is missing or mistyped fails validation even when the visible heading looks right.

## Cross-referencing a shared endpoint (resolved once, reused)

When several sibling specs consume the same endpoint (see `related_specs`), resolve it **once** and
render the **full block** (curl + TypeScript + field paths) in the single **owner** spec. In every
other spec, keep the endpoint in that spec's own `🗺️ Endpoint index` (so its data flow is complete),
but replace the detail block with a one-line reference: *"Full block in `owner-spec.md`."* plus only
the fields that spec actually reads. Never let two specs diverge on the same path/confidence.

````markdown
#### 8. Data Contract

> Resolved from the live sources via the `clubmed_api` MCP.
> **Overall confidence: <🟢|🟡|🔴> <HIGH|MEDIUM|LOW>** — <n>🟢 · <n>🟡 · <n>🔴 · <n> Developer Handoff.
> **Sources:** api (resolved live via the MCP) · directus (translation keys documented, not resolved) — **Material consulted:** <PRD06 · DRD SectionLayoutChildcare + BasketTicketLayout · glossary>.
>
> _If a family could not be resolved (e.g. DRD absent, so an editorial label has no grounding), state it here: the affected keys could not be grounded and go to the Developer Handoff._

##### ⚠️ Points to clarify — resolve before dev   <!-- dc:clarify -->

Ranked by severity. This is the first thing the developer reads in §8. Every **Blocking** row
must **also** be echoed as an `❓ Open question` in the spec's §2 Attention points.

| # | Severity | Point | Impact | Resolution path |
|---|----------|-------|--------|-----------------|
| 1 | **Blocking** | <the question that changes the implementation> | <what breaks if unresolved> | <who / where to settle it> |
| 2 | **Medium** | <uncertainty on a field / enum / schema> | <impacted surface> | <source to verify> |
| 3 | **Minor** | <detail to confirm> | <low> | <…> |

##### 🗺️ Endpoint index   <!-- dc:index -->

| Endpoint | Confidence | Role (spec need) |
|----------|------------|------------------|
| `POST /v2/childcare_search` | 🟢 high | Slot list + price + stock (BR-008) |
| `GET /v0/additional_services` | 🟢 high | Slots available per attendee (BR-008/009) |
| `POST …/cart/services` | 🟡 medium | Add slot (BR-011) |

##### 📦 Endpoints (detail)

Repeat this block per endpoint, most-critical first.

###### `POST /v2/childcare_search`

**Spec need:** <BR-xxx — what UI/logic need this answers, quoted from the spec>
**Confidence:** 🟢 high · `validate_route → is_valid: true`

**Required params**
- Headers: `x-api-key`, `accept-language`
- Body: `product_id`, `arrival_date`, `duration`, `concerned_attendees[].birthdate`

**curl** _(illustrative values — replace with your own; base URL from OpenAPI `servers`)_
```bash
curl -X POST '<API_BASE_URL>/v2/childcare_search' \
  -H 'accept-language: fr-FR' \
  -H 'x-api-key: YOUR_API_KEY' \
  -H 'Content-Type: application/json' \
  -d '{ "product_id": "MPAC", "arrival_date": "20260415", "duration": 7,
        "concerned_attendees": [{ "birthdate": "20230101" }] }'
```

**TypeScript** (fetch-based, no SDK assumed)
```typescript
const API_BASE_URL = process.env.CLUBMED_API_BASE_URL!; // from OpenAPI servers

type ChildcareSlot = {
  id: string;
  label: string;                 // localized via accept-language
  is_included: boolean;
  availability: "AVAILABLE" | string;
  price_per_attendee: number;
  currency: string;
  time_slot: "MORNING" | string; // see Points to clarify — full enum unconfirmed
  age_in_months: { min: number; max: number };
  initial_stock: number;
  remaining_stock: number;
};

async function searchChildcare(): Promise<ChildcareSlot[]> {
  const res = await fetch(`${API_BASE_URL}/v2/childcare_search`, {
    method: "POST",
    headers: {
      "x-api-key": process.env.CLUBMED_API_KEY!,
      "accept-language": "fr-FR",
      "Content-Type": "application/json",
    },
    body: JSON.stringify({
      product_id: "MPAC", arrival_date: "20260415", duration: 7,
      concerned_attendees: [{ birthdate: "20230101" }],
    }),
  });
  if (!res.ok) throw new Error(`childcare_search ${res.status}`);
  return res.json();
}
```

**Output schema (200)** — fields the spec needs (paths from the operation's response schema)
```
[].price_per_attendee : number   → unit price per attendee
[].availability       : string   → drives available / fully_booked state
[].remaining_stock    : number   → urgency (BR-016)
[].time_slot          : string   → Morning / Afternoon / Day
[].age_in_months      : {min,max}→ child eligibility
```

**Errors / edge cases**
| Code | Case | Handle in UI |
|------|------|--------------|
| 400 `FIELD_REQUIRED` | incomplete body | validate before calling |
| 404 | unknown product | fallback message |

##### 📝 CMS Keys (editorial)

**This is the only place Directus appears in a spec.** Directus is the editorial CMS that holds the
**translation keys**; this table is the contract of the keys the feature needs. The MCP does **not**
serve Directus content, so a key is never "resolved live": ground its **label text** in the
**DRD Content Contract** when one exists, and treat the **key name** as a proposal to create/confirm
in Directus. `Source` = `drd:<Component>` (label attested) or `directus` (to add / to confirm).

| Key | Real label | Source | Locales | Status | Conf. |
|-----|-----------|--------|---------|--------|-------|
| `childcare.card.tag.addons` | `"Add-ons"` | `drd:SectionLayoutChildcare` (Content Contract) | fr-FR, en-US | label attested, key to confirm | 🟡 medium |
| `childcare.slot.morning` | `"Morning"` | directus (to add — no DRD grounding) | fr-FR, en-US | dev-handoff | 🔴 low |

##### 🌍 Localization
- **API:** `accept-language` (fr-FR, en-US, …), keep the same locale across the whole journey.
- **Editorial:** per-locale keys; expected coverage + gaps.

##### 🛠️ Developer Handoff (unresolved / best-guess)   <!-- dc:handoff -->

Nothing here is confirmed against a live source. Resolving it is a developer task.

| # | Item | Family | Best-guess (unconfirmed) | Where to look |
|---|------|--------|--------------------------|---------------|
| 1 | <key / field> | editorial/business | <labeled hypothesis> | <source> |
````

## Notes for the author

- **Points to clarify first** — never bury the doubts below the data.
- **Confidence is a bucket, not a number** — `🟢/🟡/🔴 + evidence`, no percentage, no bar.
- **Severity is text** (Blocking / Medium / Minor); `🟢🟡🔴` stay reserved for confidence.
- Write the TypeScript as honest `fetch` code — do **not** invent an SDK method that may not exist.
- **Base URL** comes from the OpenAPI `servers` block; if unverified, keep `<API_BASE_URL>`.
- **Example values:** use the value documented in the OpenAPI example when present; otherwise
  use a clearly synthetic placeholder and label the block `(illustrative values)`. Never
  present an invented value as coming from a live response.
- **Security — never leak secrets or PII into a committed spec:** API keys are always
  placeholders (`YOUR_API_KEY` / `process.env.*`); never copy a real value from a live MCP
  response that could be customer data (booking ids, emails, names, account-bound prices).
  Synthetic values only.
- If a field path cannot be located in the operation's response schema, mark the entry
  `🟡 medium` and record the gap — never fabricate a path.
- Order endpoint blocks most-critical-first; the index mirrors that order.
- Every **Blocking** point to clarify is **also** listed in the spec's §2 Attention points as
  an `❓ Open question`, keeping the spec's own doubt model consistent.
